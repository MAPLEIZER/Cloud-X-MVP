Cloud-X: current state & the path to a multi-tenant SaaS

An honest snapshot of what’s built today, the hardening required before public exposure, and a two-phase plan to reach a billable, multi-tenant managed-security product.

Repo  Cloud-X-MVP Stack  React 19 · TanStack · Flask · SQLite→Postgres Updated  Jun 2026

Where it stands

A working single-tenant prototype with a strong frontend foundation and a real, end-to-end network-scanning feature. The work that defines a SaaS — server-side auth, tenant isolation, the Wazuh SIEM core, durable async, and billing — is the focus of the roadmap below. The system is a functional prototype on a trusted network; authentication, tenant isolation, and hardening are in progress before public or multi-tenant exposure.

02

Architecture: today → target

Today

  • Single Flask service · SQLite file
  • Background scans on worker threads + in-memory state
  • Access control client-side only (no server-side auth yet)
  • No tenant model — one shared dataset
  • “Nodes” tracked per-browser in localStorage

Target (SaaS)

  • API gateway → stateless workers → Postgres + Redis
  • Durable job queue; job state in the database
  • Clerk JWT verified server-side on every request
  • Org/tenant on every row; scoped queries + RBAC
  • Control plane maps tenants → Wazuh + worker nodes
03

Pre-production hardening checklist

Because Cloud-X is itself a security product, its own posture is a first-class requirement. These are the items to close before any internet-facing or multi-customer deployment, framed as remediation tasks.

P0

Authentication & authorization

Verify identity (Clerk session JWT) server-side on every API endpoint and attach the token from the client. Today access is enforced only in the frontend.

Area: backend API · web API client
P0

Harden the deployment endpoints

Require authentication, restrict to allow-listed hosts, and treat all deployment inputs as data (strict quoting / parameterised execution). Avoid logging credentials; prefer key-based / ephemeral auth.

Area: deployer · deploy routes
P0

Input validation for scans

Validate scan targets (IP / CIDR / hostname) and build scanner command-lines as argument arrays rather than strings.

Area: scanners
P0

Secrets & artifact hygiene

Remove the database file, committed virtualenv, and certificate from version control; add a .gitignore and an .env.example; move config to environment variables.

Area: backend repo hygiene
P1

Production runtime

Serve via a production WSGI server (gunicorn) as a non-root user; isolate raw-socket scanners; restrict CORS to known origins.

Area: Dockerfile · app entrypoint
P1

Data layer & async durability

Move to Postgres with Alembic migrations; run scans on a durable job queue with state persisted in the database (survives restarts, scales horizontally).

Area: backend
04

The build plan

Phase 1 makes a single-tenant product that is secure, real, and pilot-ready. Phase 2 turns it into a multi-tenant SaaS with billing. Hold Phase 2 features until Phase 1 is solid.

Phase 1

Harden & complete the core

~6–10 weeks · pilot-ready

A secure, deployable single-org product to put in front of 3–5 design-partner SMBs — with the Wazuh single-pane actually working.

A Lock down the backend

  • Server-side auth on every route + token from the client; standardise on Clerk.
  • Input validation, deployment-endpoint hardening, restricted CORS.
  • gunicorn, non-root container; isolate raw-socket scanners.
  • Purge secrets/artifacts from git; add .env.example.

B Make the core value real (Wazuh)

  • Backend Wazuh connector: agents, alerts, FIM & SCA via the Manager REST API.
  • Build the Wazuh dashboard page against it — a real SIEM single pane.
  • Adopt the standalone Cloud-X-security-agent installer as the canonical enrollment path.

C Productionise (single-tenant)

  • Postgres + Alembic; durable job queue (state in DB).
  • Real system-monitor; structured logging, error tracking, health probes.
  • Finalise nginx + HTTPS; pick an in-region host.

D Pilot deliverable

  • Monthly security & posture report (PDF) from scan + Wazuh + SCA data.
Definition of done

Every API authenticated · runs non-root over HTTPS on a cloud host · Wazuh agents & alerts visible in the dashboard · onboard an endpoint in <15 min · generate a posture PDF for one pilot org.

Phase 2

Multi-tenant SaaS & monetisation

~8–12 weeks · self-serve

Serve multiple organisations with hard isolation, self-serve onboarding, and billing — including local payment rails.

A Tenancy model

  • Organisation + Membership (map to Clerk Organizations); org_id on every table; scoped queries.
  • RBAC: owner / admin / analyst / viewer.
  • Replace the browser-local “servers” idea with a server-side tenant→node map behind one gateway.

B Wazuh isolation strategy

  • Manager-per-tenant (strong isolation) for regulated / BFSI customers.
  • Shared manager + Wazuh RBAC & per-tenant agent groups for the SMB tier.
  • Secure node ↔ control-plane comms (mTLS / signed tokens).

C Billing & plans

  • Stripe subscriptions + metered per-agent usage.
  • Local rails: M-Pesa (Daraja), Paystack/Flutterwave, priced in KES.
  • Enforce Free / Basic / Pro tiers from real usage.

D Compliance & trust (the GTM wedge)

  • Kenya DPA-aligned features: in-region residency, audit logs, data export/erasure, retention.
  • “Compliance-by-design” report templates (DPA + CIS from SCA data).
Definition of done

Multiple isolated orgs (cross-tenant access provably impossible) · per-org Wazuh data · per-org billing incl. M-Pesa · admins manage org/members/plan · audit log + data export.

Small, high-leverage steps that make the system safe to demo and unblock everything after.

1

Purge secrets from git — remove the DB file, venv/ and cert; add .gitignore + .env.example.

2

Add server-side auth — Clerk JWT verification on the backend + token from the client; restrict CORS. (Closes the open-API gap.)

3

Validate scan targets & build scanner args as arrays. (Prevents argument injection.)

4

Contain the deploy path — authenticate the deployment endpoints, fix input quoting, disable the unfinished Windows path.

5

Production runtime — gunicorn, non-root container.

6

Postgres + Alembic so the schema can evolve and data survives restarts.
