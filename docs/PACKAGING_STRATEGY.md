# Cloud-X packaging and distribution strategy

**Decision date:** 18 August 2026  
**Scope:** pre-production validation through Phase 2  
**Principle:** package the product boundaries operators actually deploy; do not turn application internals into public language packages merely because a package registry exists.

## Decision

Cloud-X **does need versioned release artifacts**, but the right artifacts are:

1. **OCI control-plane images** for the web frontend and backend/worker runtime;
2. **a versioned appliance/Compose bundle** that pins those images and carries deployment configuration, compatibility metadata and verification material;
3. **signed endpoint enrollment artifacts** for Windows, Linux and macOS as Phase 2 matures.

Cloud-X does **not** currently need a public npm package, PyPI package, Helm chart, or proprietary persistent endpoint agent.

This keeps the supported product surface aligned with the roadmap: Docker Compose first, self-hosted/private-cloud operation, Wazuh behind the `SecurityEngine` adapter, and endpoint onboarding through trusted immutable artifacts.

---

## Current repository state

The normal `.github/workflows/docker-build.yml` is a **CI build/test gate**. It builds the frontend and backend images locally and exercises runtime, migrations, Redis/RQ lifecycle and regression tests, but it does not publish those images.

That separation is correct and should remain:

```text
ordinary PR / branch CI
        │
        ├─ build frontend image locally
        ├─ build backend image locally
        ├─ run security/regression tests
        └─ DO NOT publish a product release

verified tagged release
        │
        ├─ rebuild from immutable source
        ├─ generate SBOM + provenance
        ├─ publish OCI images
        ├─ sign/attest immutable digests
        ├─ assemble Compose bundle
        └─ publish release evidence
```

A successful ordinary `main` push should not automatically become a customer-consumable package.

## Package surface 1 — control-plane OCI images

### Required images

| Image | Contents | Notes |
|---|---|---|
| `cloudx-frontend` | built React/Vite application served by nginx | immutable release image |
| `cloudx-backend` | Flask/Gunicorn API + migrations + scan/RQ worker code | API and scan-worker should use the **same release digest** with different commands |

Do not create a separate worker image unless its dependency/security boundary genuinely diverges later. Using the same backend artifact avoids version skew between the API that creates jobs and workers that consume them.

### Registry

Use **GitHub Container Registry (GHCR)** initially because the source and release workflow already live on GitHub, GHCR supports OCI images, and repository workflows can publish repository-associated packages with `GITHUB_TOKEN` plus `packages: write`.

The architecture must remain registry-portable: deployment manifests should accept an image registry/repository override so an MSP can mirror artifacts into a private registry or restricted environment later.

### Tags and immutability

Publish human-friendly tags for discovery, but supported deployment evidence must record image **digests**.

Recommended release references:

```text
ghcr.io/mapleizer/cloudx-frontend:v0.2.0
ghcr.io/mapleizer/cloudx-backend:v0.2.0

# Deployment/evidence pins these immutable values:
ghcr.io/mapleizer/cloudx-frontend@sha256:...
ghcr.io/mapleizer/cloudx-backend@sha256:...
```

Do not make `latest` the supported production/pilot install contract. A mutable convenience tag may exist later, but runbooks and evidence should pin the digest generated by the release.

### Architectures

Start with the architecture actually exercised in pilot CI/deployments (currently Linux/amd64 assumptions dominate). Add `linux/arm64` only after the full runtime and scanner dependencies are tested on that platform. A multi-architecture manifest is a support promise, not a cosmetic release feature.

## Package surface 2 — appliance / Compose release bundle

Each supported Cloud-X release should publish a small bundle such as:

```text
cloudx-appliance-v0.2.0/
├── compose.yaml
├── nginx.conf.template
├── .env.example
├── config/
│   └── security-engine-compatibility.yaml
├── scripts/
│   ├── install.sh
│   ├── verify.sh
│   ├── upgrade.sh
│   └── rollback.sh
├── manifests/
│   ├── images.json
│   └── release.json
├── SHA256SUMS
├── SBOM/
└── provenance/
```

The bundle should contain **configuration and verification material**, not duplicate container filesystems. `compose.yaml` pins the published image digests.

### Release manifest

`release.json` should eventually include at least:

- Cloud-X semantic version;
- source commit and release tag;
- frontend/backend OCI digest;
- supported architecture(s);
- compatibility-manifest version/hash;
- minimum Docker/Compose requirements;
- database migration revision;
- endpoint artifact versions/digests when Phase 2 is included;
- SBOM/provenance locations;
- release-signing identity/policy reference.

This gives support, rollback and evidence workflows one machine-readable source of truth.

## Package surface 3 — endpoint enrollment artifacts

Cloud-X is **not** creating another persistent endpoint agent. The endpoint artifact exists to verify prerequisites, configure/enroll the upstream Wazuh agent, verify health, report a structured result, and remove short-lived enrollment material.

The shared contract belongs to #93 and must precede OS-specific format decisions.

### Windows

**Pilot path:** immutable Authenticode-signed PowerShell/bootstrap artifact that verifies the upstream Wazuh MSI and supports silent RMM/Intune/GPO inputs.

**Likely supported package later:** a signed MSI/bootstrap wrapper when design partners show that MSI deployment materially improves fleet operations. Do not build an MSI wrapper solely for visual completeness.

Requirements:

- preserve upstream Wazuh Authenticode verification;
- sign Cloud-X-authored bootstrap code;
- pin the compatibility manifest/release;
- use one-time/short-lived enrollment material;
- verify service/version/first health signal;
- emit the normalized install-result contract.

### Linux

**Pilot path:** immutable signed bootstrap plus verified, pinned upstream Wazuh DEB/RPM packages/repositories.

A dedicated `cloudx-enroll` DEB/RPM becomes worthwhile only if it improves repeatable enterprise deployment or offline/restricted-network support. Do not create a distribution package merely to wrap a shell script before the enrollment contract stabilizes.

Requirements include repository-scoped signing trust, no deprecated global `apt-key`, supported upstream configuration surfaces, token cleanup and idempotent reruns.

### macOS

A signed/notarized **`.pkg` is expected to become a real supported artifact** because Apple distribution trust, notarization/stapling and deployment tooling are part of the support boundary.

The package must still verify the compatible upstream Wazuh artifact and clearly expose Full Disk Access/privacy prerequisites.

## Supply-chain requirements

A supported release is more than a successful Docker build.

### OCI images

The release workflow should:

1. check out the exact tagged commit;
2. verify the tag is on an approved `main` history produced by the promotion workflow;
3. build without reusing an untrusted mutable image as the release result;
4. publish to GHCR with repository association/OCI source labels;
5. generate SBOM attestations;
6. generate maximum practical build provenance;
7. sign immutable image digests with a pinned, reviewed Cosign/Sigstore workflow using GitHub OIDC where appropriate;
8. immediately verify the produced signature/identity policy;
9. record digests in the appliance release manifest.

### Release files

For Compose bundles and endpoint artifacts:

- generate SHA-256 checksums;
- generate an SBOM where the artifact has bundled dependencies;
- sign files or a canonical checksum/release manifest;
- retain the signature/bundle with the GitHub Release;
- verify signatures in `verify.sh` before installation proceeds.

For restricted/offline deployments, a later release profile can use an explicitly managed signing key/KMS and export OCI archives plus verification material. Do not force an internet-dependent keyless verification path on an air-gapped customer.

## Release workflow boundary

When implemented, use a dedicated workflow such as `.github/workflows/release.yml` rather than changing `docker-build.yml` into a push workflow.

Recommended trigger model:

```text
feature lanes -> dev -> staging -> main
                                │
                                └─ verified main commit
                                     │
                                     └─ signed/approved vX.Y.Z release tag
                                           │
                                           └─ release workflow publishes artifacts
```

The release workflow should use a protected GitHub Environment for any approval/secrets that should not be available to ordinary CI. Container publishing can use repository `GITHUB_TOKEN` with narrowly declared `contents: read`, `packages: write`, and any required OIDC/attestation permissions.

Do not restore “build and push backend/frontend image on every main push.” Release publishing and CI validation have different trust and lifecycle semantics.

## Versioning

Use one Cloud-X product version across the control-plane release bundle. Endpoint bootstrap artifacts may carry their own build version internally, but every supported endpoint artifact must declare which Cloud-X release/compatibility manifest it belongs to.

Before product validation, `0.x.y` semantic versions are appropriate:

- **patch:** compatible bug/security/release correction;
- **minor:** new pilot capability or supported artifact/OS behavior;
- **major:** reserve for a stable product contract after validation, not simply because the repository has existed for a long time.

Database schema revisions remain Alembic revisions, not independent product versions.

## What should *not* be packaged now

### No public npm package

The React application is a product frontend, not a reusable JavaScript library. Publishing its internal components to npm creates a compatibility/support surface with no current customer value.

### No public PyPI package

The Flask backend and scanner/engine adapters are application services, not a stable Python SDK. Keep them inside the versioned backend image until a real external API/client-library use case exists.

### No Helm chart before validation

The canonical roadmap explicitly avoids Kubernetes merely for architectural completeness. A Helm chart adds image, secrets, storage, migration, ingress and upgrade support obligations. Add it only if validated customers already operate Kubernetes and ask for it.

### No proprietary Cloud-X endpoint daemon

Continue using Wazuh as the initial endpoint/security engine. Cloud-X owns enrollment/orchestration, policy abstraction and evidence, not a duplicate persistent telemetry agent.

## Implementation order

### Phase 1 / #28

- finalize full-stack Compose + HTTPS deployment;
- define `release.json` and image digest contract;
- add release-only GHCR publishing for frontend/backend;
- attach SBOM/provenance/signature evidence;
- assemble first versioned appliance bundle;
- verify clean install + upgrade/rollback on the pilot host.

### Phase 2 / #93–#97

- stabilize shared enrollment/release schemas;
- produce signed OS-specific endpoint artifacts;
- incorporate their hashes/signatures/compatibility into `release.json`;
- gate releases on cross-platform enrollment acceptance.

### Post-validation only if demanded

- private/offline OCI archive bundles;
- DEB/RPM repository for Cloud-X-authored enrollment helper;
- Windows MSI wrapper as a primary channel;
- Helm chart/Kubernetes operator;
- external SDK packages.

---

## Release gate

Do not call an artifact a supported Cloud-X release until:

- all required CI/security checks pass on the source commit;
- no unwaived exploitable Critical/High release vulnerability remains;
- the compatibility manifest is explicit;
- image/file digests are recorded;
- SBOM/provenance is generated;
- release signatures are verified;
- migration and rollback behavior is documented/tested;
- the declared endpoint/platform support matrix has evidence behind it.

This packaging model keeps Cloud-X self-hostable and mirrorable while avoiding package formats that would add support burden before they create operator value.
